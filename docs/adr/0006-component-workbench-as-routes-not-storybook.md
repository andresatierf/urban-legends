# Component workbench lives as in-app routes, not Storybook

The component workbench is a dedicated route subtree inside the app (`src/routes/_protected/workbench/*`), not a parallel Storybook/Ladle process. Each entry is a normal route that renders a component with fixture data or against the live dev Convex deployment, registered in an explicit `src/components/workbench/registry.ts` array consumed by a sidebar.

The decision is shaped by what the workbench is *for*. Of the four goals in #111 — (1) documenting variant vocabularies, (2) iterating on design variants in isolation, (3) visual regression / QA, (4) onboarding — only (1), (2), and (4) are load-bearing. Visual regression is aspirational: there is no existing test surface, no Chromatic or Playwright snapshot infrastructure, and no concrete refactor planned that would benefit from it. The Storybook overhead amortises against (3); without (3), Storybook is over-spec'd. Goals (1), (2), and (4) are well-served by the existing `/dev/*` route pattern (Button matrix, Card demo, team-details variants for #105) once it is formalised — promoted to `/workbench/*`, given a real sidebar via `registry.ts`, and gifted shared shells (`<DemoFormShell>` for TanStack Form context, `<VariantMatrix>` for CVA primitives).

The asymmetry that tilts the decision: feature components in this codebase couple to Convex, Clerk, TanStack Form, the theme provider, and the router. Inside `_protected/workbench/*`, all of these are inherited for free — `NotificationDropdown`, dashboard panels, leaderboard, and `LoggedUserCard` render without per-component decorators. In Storybook or Ladle, each provider has to be wired explicitly via decorators or `parameters.msw`-style mocks, and Convex in particular is awkward (either point at a dev deployment or hand-roll `useQuery` mocks per story). The route-based workbench inverts that ergonomic tax to zero by default, with an opportunistic escape hatch: any component being refactored anyway can be split into container/presenter and rendered against fixtures.

## Considered options

- **Storybook 9.** Rejected: amortises against goal (3), which is not load-bearing here. Provider wiring (Convex, Clerk, TanStack Form, theme) is a permanent maintenance tax that the routes-based workbench avoids by inheriting `_protected`'s context. Storybook also wants components to be presentational; forcing every Convex-bound component to split before it can be workbenched would silently delete the most-stateful entries from scope.
- **Ladle.** Rejected: lighter than Storybook, but solves none of the provider problem — Ladle still bootstraps a parallel Vite app with its own context. The MDX/knobs win over routes is too small to justify the parallel-app overhead.
- **Storybook later, when VR becomes load-bearing.** Acknowledged. The routes-based workbench is forward-compatible: components stay presentational where it matters, fixtures are colocated and reusable, and stories can be added on top of the same components if VR ever justifies the migration.
- **Exhaustive coverage of all ~145 components.** Rejected: exhaustiveness is a goal-(3) concern (regression detection needs every component represented). Without (3), the value-per-entry curve flattens fast — variant-rich primitives and fixture-driven feature components are worth the entry; layout chrome and one-off page components are not. Target is ~40–60 entries.

## Consequences

- The workbench is not deterministic for Convex-bound entries — they render against whatever the dev deployment currently holds. Seed data drift will occasionally surface as workbench drift. Acceptable: the same drift would manifest in the real app, so the workbench reflects reality rather than fiction.
- Adding an entry is a two-touch operation: create the route file under `_protected/workbench/<area>/`, register it in `registry.ts`. No magic file-tree discovery. The explicitness is the feature — `registry.ts` is the canonical sidebar source and the place to look for "what's actually in the workbench."
- Fixtures are colocated with the component (`*-workbench-fixtures.ts`) rather than with the route. This survives feature-folder refactors and keeps fixtures close to the components they fixturise.
- Migrating to Storybook later is feasible but not free: each entry would become a `*.stories.tsx` story, and provider decorators would need to be authored. The fixtures and presentational refactors carried out for the workbench would port directly.

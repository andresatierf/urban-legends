# Adopt Fallow as an agent-invoked code-health signal

Fallow (https://docs.fallow.tools/) is wired into the repository as an **agent-invoked, on-demand** code-health signal — not a CI gate, not a periodic cron, not an MCP server. The agent shells out to `npx fallow <subcommand>` through Bash, parses stdout in-context, and proposes cleanups within the same session. A checked-in Fallow config file carries excludes (starting at `convex/_generated/**` only). Subcommand intent mapping and caveats live in `docs/agents/fallow.md`, discoverable from a one-liner in `CLAUDE.md`.

The decision is shaped by what Fallow is *for* in this repo. Of the four candidate roles — (1) blocking CI gate, (2) periodic cleanup signal feeding a dashboard, (3) on-demand inspection invoked by an agent, (4) MCP-integrated structural tool — only (3) is load-bearing today. There is no recurring "code-health review" ritual; cleanup work happens reactively after variant explorations or refactors, exactly when an agent is already in the loop. Wiring Fallow into CI or a cron would produce a signal that nobody is responsible for consuming, and an MCP server carries persistent context-window cost that doesn't pay back for a tool invoked maybe weekly. The single-session, agent-driven loop matches the actual cleanup cadence.

The asymmetry that tilts away from MCP: Fallow's CLI is already TS-native and human-readable, and Claude Code can parse its stdout fine. The structured-tool win MCP would buy is small for inspection-only workflows. The cost — `.mcp.json` entry checked in, every contributor's Claude Code session paying tool-definition tokens whether or not Fallow gets used — is paid every turn. The ratio doesn't justify it at this volume. MCP becomes interesting if and when usage grows or the workflow shifts to a persistent report that needs structured diffing across runs.

## Considered options

- **CI integration (blocking or non-blocking job).** Rejected: produces a signal with no owner. The issue body itself frames Fallow as a "periodic cleanup signal, not a blocking gate" — but in this repo there is no recurring review ritual that would consume a non-blocking signal. A nightly GHA producing a report nobody reads is worse than no report. Cleanup happens reactively; the trigger should be reactive too.
- **Persisted report (`workflow_dispatch` or `bun fallow:report` → `.fallow/report.json`).** Rejected for v1: useful only if you want historical signal ("is this getting better over time?") or asynchronous agent pickup ("agent reads last week's report"). Neither is in scope. Adds artifact storage decisions (git-ignored vs committed, retention, schema stability) that buy nothing in the single-session loop. Forward-compatible: switching to a persisted report later does not invalidate any of this decision.
- **MCP server.** Rejected for v1, with explicit revisit door. The static-layer CLI is enough for inspection; MCP's structural advantages amortise against repeated, high-frequency, tool-call-shaped usage that this workflow does not produce. Persistent context cost is the killer. Revisit if Fallow usage becomes routine enough that MCP's per-turn cost is dominated by its query savings.
- **Wrapper script aggregating all subcommands (`bun fallow` runs `dead-code` + `dupes` + `health`).** Rejected: ritual-completeness framing without a ritual. The agent already picks the right subcommand per intent in a single-session loop; pre-bundling forces it to parse noise from analyses the current task didn't need. The `docs/agents/fallow.md` intent map carries the routing instead.
- **Agent invocation of `fix --dry-run`.** Rejected: keeping `fix` as a human-only verb. Letting the agent run Fallow's auto-fix even in dry-run mode invites it to mechanically transcribe proposed edits instead of reasoning about them. The agent calls inspection subcommands; the human invokes `fix` directly when they want to see what Fallow itself would do.
- **Maximal excludes from day one** (e.g. shadcn `ui/**`, `routeTree.gen.ts`, fixtures). Rejected: noise we cannot characterise without first-run data. Excludes accumulate reactively after the first run reveals what Fallow flags as genuinely-vendored vs genuinely-stale. Starting minimal protects against pre-emptive suppression of real signal.

## Consequences

- Fallow is invoked by the agent through Bash, not via a tool API. Stdout format changes between Fallow versions could silently break the agent's parsing. Mitigation: `docs/agents/fallow.md` records a pinned-or-tested Fallow version, bumped deliberately rather than automatically.
- There is no historical signal — every run is fresh. "Is the repo getting healthier?" cannot be answered without either re-running Fallow on past commits or graduating to a persisted-report model. Acceptable given the reactive cleanup cadence.
- oxlint and Fallow overlap on dead-code detection but at different granularities — oxlint operates intra-file (unused imports, unused locals, unused params), Fallow operates cross-file (unused files, unused exports, unused dependencies). The agent's posture, documented in `docs/agents/fallow.md`: trust oxlint for the things it catches (it runs in CI and is auto-fixable); reach for Fallow when the question is cross-module or repo-shaped.
- Adding Fallow as a `devDependency` is optional; the `npx fallow` invocation pattern works without installation. The ADR does not commit to installing it — that is a tactical choice for the implementing PR based on whether `bunx` cold-start cost is annoying enough to justify the lockfile entry.
- The MCP door is left explicitly open. A follow-up issue should be filed if the team finds itself running Fallow more than a few times per week; that is the trigger to revisit MCP. Until then, no `.mcp.json` entry for Fallow ships.
